# Deployment

## Local development

Use the Python commands in README.md. Local SQLite starts without external credentials. Configuration is read from the process environment. For local Bash use `set -a; source .env; set +a` before starting Uvicorn. Set PUBLIC_ORIGIN to http://localhost:8000 for that port. Compose uses http://localhost:8080.

## Docker Compose

Install Docker with Compose v2. For local development run `python -m scripts.configure_local` from the repository root. It creates database and session secrets and prompts for an optional owner password. For manual configuration, copy .env.example to .env. Set POSTGRES_PASSWORD to a random hexadecimal value, for example one generated by `openssl rand -hex 32`. Use the same command with a new random value for APP_SECRET. Place the output of `python -m scripts.admin_password` in ADMIN_HASH to enable the dashboard. Keep .env private.

```sh
docker compose up -d --build --wait
docker compose ps
curl -f http://localhost:8080/api/health
```

The web entry point binds to localhost:8080; database and app ports stay internal. Alembic runs before the app starts. The migration is retryable on subsequent starts. Stop with `docker compose down` to preserve the volume.

## Integrations

- GitHub REST works without authentication subject to public rate limits. Add GITHUB_TOKEN for the contribution calendar. Use a token limited to public data. Keep it server-side.
- Production email needs SMTP_HOST, SMTP_PORT, SMTP_SECURITY (starttls or ssl), MAIL_FROM and MAIL_TO, plus SMTP_USER and SMTP_PASSWORD for authenticated providers. Use a verified sender.
- To test locally set SMTP_HOST=mailpit, SMTP_PORT=1025, SMTP_SECURITY=local, MAIL_FROM=portfolio@example.test and MAIL_TO=owner@example.test. Run `docker compose --profile mail up -d --build --wait`. The local inbox is at http://localhost:8025. Development acceptance is labelled in the form.

## Existing HTTPS host

Use an existing domain and a host with Docker. Set APP_ENV=production and PUBLIC_ORIGIN to the final HTTPS origin with no trailing slash. Configure HTTPS at the host reverse proxy and forward to 127.0.0.1:8080. With Caddy on the host, use the following Caddyfile, substituting your domain:

```
portfolio.example.com {
    reverse_proxy 127.0.0.1:8080
}
```

If an outer proxy sits in front of Compose, configure Nginx real_ip_header and set_real_ip_from **only for that proxy’s trusted address**. Otherwise visitors behind that proxy can share a rate-limit bucket and visitor estimate. Uvicorn trusts forwarded addresses only from the fixed internal Nginx address. An overlapping Docker subnet requires adjusting compose and the trusted Nginx address together.

Set APP_VERSION and BUILD_ID from the release. Set DEPLOYED_AT only after a known successful deployment. Verify health, HTTPS origin, private sign-in, logout and an actual delivered message after configuration.

The verification workflow tests, builds, starts the Compose stack and runs browser checks. The manual deployment workflow requires an existing, isolated self-hosted runner labelled portfolio-production and a protected production environment. Store the production .env text as PORTFOLIO_ENV in that environment. Dispatch only a verified main revision. No hosting account is provisioned by the workflow.

## Backup and recovery

```sh
docker compose exec -T db pg_dump -U portfolio -Fc portfolio > portfolio-backup.dump
```

Store backups outside the public repository, encrypt them and restrict access. Test restoration into a fresh database before switching the app:

```sh
docker compose exec -T db createdb -U portfolio portfolio_restore
docker compose exec -T db pg_restore -U portfolio -d portfolio_restore < portfolio-backup.dump
```

If health fails, inspect `docker compose logs app db`. An existing database volume retains its original password. Resolve environment mismatches before retrying. If contact reports unavailable, check the configured sender, recipient, TLS mode and SMTP provider. If WebGL is unavailable, the illustrated workspace and all six keyboard controls still work.

## Free Render service with Neon PostgreSQL

1. In [Neon](https://console.neon.tech/), create a Free project. From **Connect**, copy the direct PostgreSQL URL including the TLS parameters. Store this in the hosting dashboard only.
2. From the repository root run `python -m scripts.admin_password`. Choose the password you will use at /admin. Copy the generated hash.
3. Open [Deploy to Render](https://render.com/deploy?repo=https://github.com/alishapandit228/girl-in-the-cloud) in a Hobby workspace. Confirm the blueprint lists one Free web service. Set DATABASE_URL to the Neon URL and ADMIN_HASH to the generated hash. Render generates APP_SECRET. On the generated onrender.com domain, the startup script uses Render's HTTPS origin and port automatically.
4. Once the service is live, open /api/health, then /admin, and verify sign-in. Add GITHUB_TOKEN as a server-side secret for the contribution calendar.
5. For contact delivery use an SMTP provider supporting STARTTLS on port 2525, such as SMTP2GO Free. Set SMTP_HOST to the provider's assigned hostname, SMTP_PORT=2525, SMTP_SECURITY=starttls, SMTP_USER, SMTP_PASSWORD, MAIL_FROM (verified sender), and MAIL_TO (your inbox). Submit one message and confirm receipt. Without these settings the form reports delivery unavailable.

The Free service sleeps after idle periods and the first visit can take about a minute. Free quotas apply at both providers. Keep the accounts on free plans. The Blueprint provisions no database, disk, worker or paid instance. Forwarded client IP headers are disabled on this deployment: visitors behind the same proxy can share rate limits and a daily visitor estimate. For a custom domain, explicitly set PUBLIC_ORIGIN to its HTTPS URL.
